# 命理排盘实战规范（Mingli Paipan Practice）

跨引擎排盘实战中沉淀的操作规范。本 skill 负责**排盘的流程与陷阱**，具体算法在各排盘 skill（bazi-paipan 等）中。

## 时辰流派分歧（最重要的实战坑）

出生时间存在两种排法，**必须向用户展示分歧并让其确认**：

| 派别 | 依据 | 适用 |
|---|---|---|
| **钟表时派** | 严格按记录的当地时间（现代排盘默认，mingyu 默认） | 用户确认记录的是钟表时间 |
| **真太阳时派** | 经度修正 + 均时差（传统派） | 用户记录的是当地日影时间，或出生地经度偏差大 |

**处理流程**：
1. 先算真太阳时差：`offset = (经度-120)*4 分钟 + 均时差(EoT)`；列出每个钟点对应的真时辰表
2. 展示给用户：「你的 7-9 点北京时间，在某地真太阳时是 4:55-6:55，实际是卯时而非辰时」
3. **问用户记录的是北京时间还是当地钟表时间**——确认后选对应版本
4. 无法确认 → 两版都排，输出标注"时辰流派分歧"，主推钟表时版（现代默认）
5. 能确认分钟 → 精确到分钟重排

## 西部省份时差速查（经度 <110°E 必查）

| 城市 | 经度 | 时差 | 备注 |
|---|---|---|---|
| 新疆某地 | 88.5°E | ≈-125 分钟 | 7-9点→卯时 |
| 乌鲁木齐 | 87.6°E | ≈-130 分钟 | 整格错位常见 |
| 拉萨 | 91.1°E | ≈-116 分钟 | 同上 |
| 西安 | 108.9°E | ≈-44 分钟 | 边界，<110 需算 |
| 成都 | 104.1°E | ≈-64 分钟 | 需算 |

**⚠️ 经度 >110°E 也不能跳过边界检查**（2026-08-19 河北某市案例）：河北某市 114.5°E 时差 ≈-22 分钟（1月初均时差再 ≈-3.5 分钟），示例命主庚 钟表时 **11:00-11:25 → 真太阳时 10:35-11:00 = 巳时**——跨格，午时盘的紫微/婚姻结论全变。**凡出生时间落在时辰边界前后 30 分钟内，无论经度多少都必须算真太阳时并展示两版时辰**；用户报时间区间（如"11-12 点"）时必须算边界分钟并追问具体分钟。

## 跨引擎交叉验证

同一生辰用多个引擎排盘，结果应一致（四柱必须完全相同）：
- mingyu MCP / mingyu-core（Node，iztro+tyme4ts）
- **mingpan 远程 MCP**（`https://mingpan.bzwai.com/mcp`，2026-09-21 接入，**独立实现**；18 工具：八字/紫微全套含**流月流日**、六爻/梅花/大六壬/奇门 + `qimen_yongshen`（14 事类用神分析，含诉讼/求职/婚姻）、节气精算、历法互转）——**重启 Hermes 后生效**，第二验证引擎
- **零依赖引擎 `bazi-paipan/scripts/zero-dep/pai_pan.py`**（纯 Python 标准库，2026-09-21 吸收自 jinchenma94/bazi-skill ⭐3154）——最稳回退；已验证 示例命主甲 辰男、示例命主丁 酉男与 mingyu/iztro 一致
- bazi-python 详盘（Python，lunar_python 系）
- paipan.py（Python，lunar_python 兼容层）
- bazi-ziwei skill calculator（Node，Yiqi core）

**⚠️ 性别必须问清——它改变大运顺逆，不改四柱**（实测 2026-08-07）：
- **四柱与性别无关**：同一生辰男/女排出的乙丑 乙酉 甲子 甲戌完全相同
- **大运方向由"年干阴阳 × 性别"决定**：阳男阴女顺行，阴男阳女逆行。乙丑年（乙为阴）：男命逆行（甲申癸未壬午…），女命顺行（丙戌丁亥戊子…）——**两条大运完全不同，当前所处大运也不同**
- 例：示例命主乙 戌时，41 岁：男命在己卯运，女命在己丑运——解读差异巨大
- 紫微同理：阴阳（阴女/阳男）决定大限顺逆
- **bazi.py 女命加 `-n` 参数**，bazi-ziwei calculator 用 `--gender=female`

**发现不一致时**：先查真太阳时/农历参数是否传错，再查引擎流派差异（如紫微四化有飞星/三合派之分），最后查参数类型陷阱。

**⚠️ 紫微星位置随时辰变——"星曜只由生日定"是认知误区**（2026-08-19 查 iztro 源码确认）：iztro 起局用**命宫干支定五行局**（star/location.js getStartIndex → getFiveElementsClass(命宫天干, 命宫地支)），命宫地支由生月生时定 → **同一生日不同时辰 = 五行局/紫微位置/命宫全不同的两张盘**。实测 示例命主庚：午时=金四局/紫微在辰/命宫未（无正曜借日月）；巳时=火六局/紫微在午/命宫申破军。**两版星曜落宫不同是正统算法（五行局随命宫变），不是引擎错**。iztro timeIndex 口径与 mingyu 一致：0=早子时(0-1点)…12=晚子时（lib/data/types/astro.d.ts:191）；dayDivide 配置：current=晚子时算当天，forward=算来日。**安星口诀手推极易错（紫微系/天府系排布、同宫组合），以引擎输出为准；引擎输出异常先查源码/类型定义再下结论，勿凭记忆断言引擎错**。

## mingyu-core 本地调用回退（MCP 不在会话时）

MCP 工具只在会话启动时注入；早于 MCP 配置的会话没有 `mcp__mingyu__*` 工具，但可以直接 import mingyu-core（在 `C:\Users\Administrator\Documents\mingyu` 下运行）：
```js
import { generateAstrolabe } from 'mingyu-core/divination/astrolabe';
generateAstrolabe({ year: '1985', month: '6', day: '8', hour: '6', minute: '0',
  latitude: '42.3', longitude: '88.5', timeZoneId: 'Asia/Shanghai' });
```
**参数陷阱**：
- 数值参数**必须是字符串**（requireNumber 校验 typeof === 'string'），number 会报「星盘需要填写有效的出生年份」
- 时区用 `timeZoneId: 'Asia/Shanghai'`（IANA 名），或纯数字字符串 `timezone: '8'`；`'+08:00'` 被正则拒
- 导出名先查 dist 源码 `^export`（如 generateAstrolabe 而非 astrolabeCalculator）
- 子路径必须存在于 package.json exports，否则 ERR_PACKAGE_PATH_NOT_EXPORTED
- 详见 hermes-mcp-setup skill 的 references/mingyu-mcp.md

## MCP 排盘响应过大被截断 → 本地脚本精排（2026-08-19 盲测实测）

`bazi_calculate` / `ziwei_calculate` 返回可达 29-30 万字符（全量证据 JSON），MCP 结果会在沙箱被截断：四柱可见，但**藏干、大运、神煞、紫微全宫位、四化全部丢失**。盲测/详盘场景别依赖 MCP 完整输出——直接在 mingyu 目录写临时脚本 import iztro + mingyu-core 只打印所需字段（跑完即删 + `git status --short` 确认干净）。

**⚠️ 更极端的一档：合盘类工具（`bazi_compatibility` / `ziwei_compatibility`）单次返回 ~72-74 万字符**——连 preview 都只是开头。这类**不要重跑**：工具层会自动把全文落盘到 `cache/terminal/hermes-results/call_*.txt`，用脚本解析该文件（注意 `{"result": ...}` 可能套 dict 也可能套 JSON 字符串，需循环 unwrap；紫微合盘的结论在 `evidence.items[]` 而非空壳的 `palaceOverlays[]`）。字段路径与可复用解析片段 → `references/mcp-compat-output-extraction.md`

**iztro 字段名（实测 示例命主庚 午时女）**：
- `astro.bySolar('1987-1-1', 6, '女', true, 'zh-CN')`，timeIndex 6=午时，与 MCP timeIndex 口径一致
- 宫位支：`palace.earthlyBranch`（**不是 branch/location**，那俩是 undefined）
- 身宫：`a.earthlyBranchOfBodyPalace` / `a.bodyPalaceName`（不是 bodyPalace 对象）；命宫枝用 `palaces.find(p=>p.name==='命宫').earthlyBranch`
- **`a.soul` / `a.body` = 命主/身主，不是命宫主星！** 命宫主星 = `palaces.find(p=>p.name==='命宫').majorStars`（可能为空=命无正曜，借对宫看）
- 四化：`palace.mutagen` 实测 undefined 不输出；用年干四化口诀手推（如丙=天同禄/天机权/文昌科/廉贞忌）或查 iztro `selfMutaged()` 方法
- 大限：`palace.decadal` = {range, ganZhi, ageRange}
- palaces 数组是**顺时针**顺序（命宫在中间），不要假设下标顺序；大限顺逆=阳男阴女顺行、阴男阳女逆行

**mingyu-core bazi 字段名**（`calculateBaziChartFromInput`，school:'ziping'，`r = res?.result ?? res`）：
- 大运：`r.luckInfo.cycles[]`（首条 isXiaoyun=小运需跳过；每条 ganZhi + startSolarTime + age）+ `r.luckInfo.startInfo`（"出生后 X 年 X 月 X 天起运"文本）、`r.luckInfo.handoverInfo`（交运日期）
- 强弱/格局/用神：`r.analysis` = `dayMasterStrength.status`（身弱/身强）、`mingGe.pattern`（伤官格等）+ `isKuiGang`（魁罡日）、`usefulGod`（favorable/unfavorable/primaryUseful/primaryReason/strategyTrace 含调候规则）
- 其他：`r.tenGods`（天干十神）、`r.hiddenTenGods`（藏干十神）、`r.shensha`（神煞按年/月/日/时/global 分组）、`r.nayin`、`r.kongWang`（空亡）、`r.wuxingStrength`、`r.mingGong`/`r.shenGong`、`r.mingGua`
- **`r.pillars[*]` 只有 gan/zhi/ganZhi 三个字段**——没有 ganTenGod/hiddenGans，猜字段名会得 undefined；藏干十神看 r.hiddenTenGods，天干十神看 r.tenGods

**八字 vs 紫微月柱差异（流派口径，非排盘错误）**：同一生辰，八字引擎月柱按**节气**（如庚子），iztro 的 chineseDate 月柱按**农历月**（如辛丑）——安星不受影响，解读时标注"紫微引擎月柱按农历"即可，不要当 bug 排查。

## 盲测模式（只给生辰、不交代背景，2026-08-19 实测）

用户说"盲测/只看盘/先别告诉我背景"时，是**能力检验场景**：用户会拿真实经历逐条核对，断语必须具体到可验证，不能含糊。默认钟表时直排 + 声明参数完整度（出生地未知→注明未做真太阳时校正）。

流程：
1. 照常排盘（八字+紫微双引擎交叉），输出"排盘框架"：四柱、大运序列、紫微简盘（命宫/夫妻/财帛/官禄等重点宫）、星座等中西互证锚点
2. 十项盲断固定维度：**性格/事业/婚姻/异性缘/财富/健康/六亲/大运回顾/当前流年/命理特质**——每条**必须附证据**（格局、神煞、星曜、古籍口诀），无证据的断语不写
3. 敢断具体时间窗：婚姻给大运窗口+年份区间（如"正缘窗口 29-39 丁酉运，2016-2018 或 2020-2022"），大运回顾给验证点年份（如 2017 官星双现、2020 伤官见官）——具体才可被验证；忌用"可能/也许"堆砌安全断语
4. 结尾固定"验证请求"清单（婚否/职业/父母关系/性格/出生地），明示反馈用于**校准用神与婚期判断**（用户偏好：实际运势是校验用神判断的最高证据）
5. 命局最大课题（如婚姻）放最前、写最透；参数声明不可省（时辰流派、真太阳时、引擎、紫微月柱按农历的差异）

## 各引擎参数格式

| 引擎 | 日期参数 | 陷阱 |
|---|---|---|
| bazi-python (bazi.py) | **农历**年月日 + **小时数**(0-23) | **时辰参数是"小时数"不是时辰序号**：戌时(19-21点)传 20，传 12 会错成午时！传公历会错盘，公历先转农历 |
| paipan.py | 公历 + 时/分 | 无 |
| bazi-ziwei calculator | 公历 + hour/minute | --json 输出重定向勿 2>&1 |
| mingyu bazi_calculate | 公历 number | timeIndex 必填 |
| mingyu *_prompt | 公历 **string** | question 必填，promptTopic 枚举 |
| mingyu astrolabe_prompt | 公历 number | timeZoneId 必填 |
| mingyu generateAstrolabe | 公历 **string** | 返回结构 `raw?.result ?? raw`（无 .result 顶层） |

## 问事卦纪律：一事不二占与焦虑型占问（2026-09-15 实战）

- **"怕事情拖到凶月撞上高危日"的答法（时间撞车推演，2026-09 实测）**：**不起新卦**（一事不二占），用已有数据推演，分两层答——①**性质 vs 强度分开**：已锁定的性质不因时间推移改变，凶月只是"压力/摩擦峰值"（身心难受），不是"结果落地"；②**拆弹**：前置月把能推进的程序推完（每推进一步=凶月少一个节点=少一次撞车），配错期 + 当日应对脚本（只走律师/不签/不喝酒/早睡）

## 用户上传命盘/指令截图 → Windows OCR 提取（2026-08-08 验证）

$null = [Windows.Graphics.Imaging.BitmapDecoder,Windows.Graphics,ContentType=WindowsRuntime]
# 定义 Await 函数（AsTask 泛型包装）→ StorageFile.GetFileFromPathAsync → OpenAsync → BitmapDecoder.CreateAsync → GetSoftwareBitmapAsync → OcrEngine.TryCreateFromUserProfileLanguages() → RecognizeAsync($bitmap) → $result.Text

## 子时（23:00-01:00）跨日分歧（2026-08-08 实测）

用户报"23-1 点之间"时，**必须区分晚子时/早子时并展示两种时柱**，实测（1989-04-11 女）：

```
晚子时 23:30 → 时柱 庚子（日柱辛丑不变，属当天）
早子时 00:30 → 时柱 戊子（日柱辛丑不变，属当天）
```

**⚠️ 关键分歧**：部分流派把 23 点后算作**次日**——日柱会整体后移（辛丑 → 壬寅），全盘重排。这是"晚子时"最大的流派分歧，**必须问清"23 点多还是 0 点多"**，只给"23-1 之间"时两版并列输出。

**处理流程**：
1. lunar_python 分别排 23:30 和 0:30 两版四柱（`Solar.fromYmdHms(年,月,日,23,30,0)` / `(...,0,30,0)`）
2. 若两版**时柱不同但日柱相同**（本例）→ 展示差异，问用户靠近哪端
3. 若用户仍不确定 → 默认按"当天日柱"排并标注流派假设，紫微/时柱相关结论标"待精确时辰"
4. 真太阳时修正后仍可能落回原时辰（河北某市 -23 分钟：23:30→23:06、0:30→00:06，均在子时内）——**先修正再判是否跨格**

## 用户实况反驳的校准流程（2026-09-21 感情线实战，必守）

用户以**现实经验反驳某条断语**时（本例："我感情这边都在一起 5 年了，怎么能突然就发现呢？"），标准六步——**既不能硬拗，也不能把结论整条撤掉**：

1. **先认用户的经验是真实数据**（"5 年没翻车说明隐蔽性一直做得好，这一点我认，不否认"）——本用户明确说过"实际运势是校验用神判断的最高证据"，反驳=输入，不是挑衅
2. **降权被反驳的那条线**：配偶侧"被发现"概率调低（用户实证支撑），但**不撤结论**
3. **检查应象主体是否被误读**——这是关键动作：同一组象换个主体就与用户经验兼容。本例：廉贞忌=**关系内部生刺**（不是对外暴露）、官符落夫妻+文曲忌=**对方要名分/条件（文书化）**、亥合寅=**亲密关系状态变化** → 结论从"会被发现"改为"**她那边要动**"
4. **补入被用户忽略的变量**：用户自身的状态变化（收缩/撤退/忙）会被对方感知 → 触发对方主动摊牌；对偶年龄/生育/再婚窗口等硬时间成本是现实燃料
5. **把风险落到可核对的三件**：主体（谁动）+ 方式（要价/摊牌/条件）+ 时间窗（哪个月），并给一句可记住的定性（"你不是怕被发现，是怕被要求——被要求只跟她的时间表有关"）
6. **校准入档**：写进 Obsidian 档案对应小节，注明"校准前/校准后"对照表，避免下次误读

**原则**：现实反馈校准的是**读法**，不是让结论松动；结论依然锁死（见"铁断纪律"）。

## 合盘/感情判断的诚实纪律（2026-08-07 用户摊牌后教训）

1. **关系定性必须基于完整事实**：用户先说"有姑娘喜欢我"（问采不采），后摊牌"已婚、她是离异、已 5 年"——**完整背景会推翻前一版的结论**（从"要不要开始"变成"5 年关系怎么办"）。先问清关系状态（是否已婚/对方婚否/多久），再下判断

## 时代运 × 个人运（流年判断的背景维度）

判断"为什么这两年特别难/顺"时，个人大运之上还有时代气候，**三层叠加**：

```
时代气候（三元九运，20 年）
  └─ 年份气候（赤马红羊等火年）
       └─ 个人大运（十年）+ 流年（一年）
```

**三元九运**：八白艮土（2004-2023，房地产）→ **九紫离火（2024-2043，AI/数据/电子/虚拟/光电）** → 一白坎水（2044-2063）。
**赤马红羊**：丙午（赤马）、丁未（红羊）两年，源出南宋柴望《丙午丁未议》（靖康之变 1126-1127 正是丙午丁未）。本质是"火年中的火年"，非神秘劫数。

**应用**：喜水忌火之命逢 2024-2043 火时代 + 2026/2027 火年 = 天地人三层皆火，诸事不顺是五行应期；行业方向仍可做火行业（AI/数据），但姿势要"以水济火"——做流通节点、信息差、撮合，不做重资产重规模（燃烧角色）。详见 Obsidian 命理档案中 示例命主甲 命例的 8.4 节（大运×九紫离火×赤马红羊三重叠加分析）。
